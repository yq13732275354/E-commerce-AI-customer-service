## 1. 背景与目标

### 1.1 背景

现有 v1.0 采用「场景短清单 + LLM 选编号 + 主键查表」的确定性召回，优点是可控、可归因，但随着两类变化已不够用：

- **新增产品咨询场景**：无结构化方案库，问题形态发散（尺码、材质、库存、搭配），无法枚举成短清单；
- **用户问法口语化**：同一个意图有大量同义表达（“多久发货 / 什么时候能发 / 今天能走吗”），短清单靠模型理解，稳定性依赖模型状态。

### 1.2 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 四类场景都能答，且答得准 | 场景分诊准确率 ≥ 92% |
| G2 | 口语化问法也能召回正确知识 | Recall@1 ≥ 85%，Recall@3 ≥ 95% |
| G3 | 答案只来自知识库，不编造 | 接地率 100%，数字幻觉 0 条 |
| G4 | 语料可持续迭代、可回归 | 每次改语料可一键重跑评测并对比 |
| G5 | 运营改知识不发版 | 知识对热更新 + 索引重建接口 |

### 1.3 非目标（明确不做）

| 不做 | 说明 |
|---|---|
| 公网部署 / 鉴权 / 多租户 | 仅本机 localhost，单店铺 |
| 多语言、语音、图片消息 | 纯中文文本 |
| 真实工单系统闭环 | 仅输出 `escalate` 字段与转人工话术 |
| 管理后台 UI | 直接维护 `kb_pairs` 表 + 重建索引 |
| 高并发 / 分布式 | 单进程 + SQLite，千级向量 |

## 2. 用户与使用场景

| 角色 | 诉求 |
|---|---|
| 消费者 | 用一句话问清楚：能不能买、什么时候到、怎么付、怎么退 |
| 客服运营 | 改话术、改时效、补知识，不重启服务、不发版 |
| 开发者 | 能定位「召回错」还是「选号错」，能回归评测 |

典型对话路径：

1. 售前：问材质 / 尺码 / 库存 → 产品咨询；
2. 下单后：问发货时间 / 物流进度 / 改地址 → 物流发货；
3. 支付环节：问支付失败 / 扣款 / 优惠券 / 退款到账 → 支付；
4. 收货后：问退货 / 换货 / 破损 / 保修 → 退换货。

## 3. 场景体系与归属规则

### 3.1 四个场景

| 场景码 | 名称 | 覆盖范围 | 标准问目标 |
|---|---|---|---|
| `product` | 产品咨询 | 餐椅 28、吧椅 26、连衣裙 26 | 80 |
| `logistics` | 物流发货 | 发货、快递、运费、地址、签收、延误 | 70 |
| `payment` | 支付 | 支付方式、扣款、优惠、发票、退款到账 | 60 |
| `aftersales` | 退换货 | 退货、换货、破损、保修、售后时效 | 60 |
| — | 合计 | — | **270** |

> 产品咨询不再做“泛品类通用问答”，而是绑定 3 个真实商品：白蜡木餐椅、碳钢升降吧椅、法式碎花连衣裙。答案只能引用 `data/corpus/product_catalog.yaml` 的字段，禁止自由发挥。
> 原需求中的“物流支付”“物流退换货”不再作为独立场景，分别并入 `payment` 与 `aftersales`。

### 3.2 场景边界判定（分诊优先级）

分诊按以下顺序判定，命中即停，避免多标签摇摆：

1. 出现**商品属性**（材质 / 尺码 / 颜色 / 型号 / 库存 / 怎么洗）→ `product`
2. 出现**包裹动作**（发货 / 快递 / 签收 / 地址 / 运费）→ `logistics`
3. 出现**资金动作**（支付 / 扣款 / 优惠券 / 发票 / 到账）→ `payment`
4. 出现**商品处置**（退 / 换 / 修 / 破损 / 少件）→ `aftersales`
5. 以上都不明确 → `none`，走澄清或转人工

## 4. 知识库设计（防重叠核心）

### 4.1 知识对的定义

一条知识对 = **一个意图 + 一个标准答案 + N 条同义问法**。同义问法只是检索入口，不重复生成答案。

| 字段 | 含义 | 约束 |
|---|---|---|
| `pair_id` | 唯一编号，如 `payment-refund-eta-001` | 场景码-子场景-序号 |
| `scenario` / `sub_scenario` | 场景与子场景 | 必须落在覆盖矩阵内 |
| `canonical_question` | 标准问法 | 一条知识对只有一个 |
| `answer` | 标准答案 | 40~120 字；数值必须用占位符 |
| `conditions` | 条件（已发货 / 未发货等） | 有分支必须拆条，不得写进同一答案 |
| `policy_level` | `stable` / `configurable` / `sensitive` | `sensitive` 必须人工审 |
| `paraphrases` | 同义问法 3~5 条 | **全局唯一**，不得跨知识对重复 |

### 4.2 覆盖矩阵（子场景与配额）

产品咨询按 3 个 SKU 展开（已落地于 `data/corpus/product_qa.jsonl`）：

| SKU | 子场景分布 | 条数 |
|---|---|---|
| 白蜡木餐椅 `p1_dining_chair` | 尺寸 5、材质 4、承重 4、库存 3、搭配 3、价格 3、安装 3、保养 3 | 28 |
| 碳钢升降吧椅 `p2_bar_stool` | 尺寸 5、材质 3、承重 4、库存 3、搭配 3、价格 2、安装 3、保养 3 | 26 |
| 法式碎花连衣裙 `p3_dress` | 尺码 5、面料 4、参数 4、库存 3、搭配 3、价格 2、洗涤 3、适用人群 2 | 26 |

其余三场景：

| 场景 | 子场景 | 条数 |
|---|---|---|
| logistics | 发货时效、预售备货、快递公司、指定快递、运费、改地址、改电话、拦截退回、签收异常、物流不更新、延误 | 各 6~7 |
| payment | 支付方式、支付失败、重复扣款、已扣未支付、优惠券、分期、发票、退款到账、退款进度、支付安全 | 各 6 |
| aftersales | 售后入口、七天无理由、运费承担、质量问题、破损少件、换货、维修保修、超时未处理、拒收后退款 | 各 6~7 |

**规则**：每个子场景至少 6 条，空白格不允许上线；同一问法全局唯一；产品参数类问题必须能追溯到商品事实表字段。

### 4.3 七条唯一归属原则

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | 单一意图 | 一条知识对只解决一个可执行诉求 |
| P2 | 单一主语 | 资金 → payment；商品 → aftersales；包裹 → logistics；属性 → product |
| P3 | 动作归属 | 发起退货 = aftersales；包裹拦截/改地址 = logistics |
| P4 | 不重复答案 | 答案不得整段复述另一条答案，相似度 > 0.85 必须合并 |
| P5 | 一问一答 | 同一问法全局只归属一条知识对；冲突时保留更具体的那条 |
| P6 | 条件外置 | 已发货/未发货等分支必须拆成独立知识对 |
| P7 | 时效归属 | 只说“多久”无主语 → logistics；说“退款到账” → payment |

### 4.4 易重叠问题的归属决策表

| 典型问法 | 归属 | 理由 |
|---|---|---|
| 退款多久到账 | payment | 主语是资金到账 |
| 退货后多久退款 | aftersales | 主语是退货流程，答案内说明到账时效 |
| 拒收后怎么办 | logistics | 动作发生在包裹环节 |
| 拒收后钱怎么退 | aftersales | 诉求落在退款 |
| 商品能不能退 | aftersales | 处置对象是商品 |
| 优惠券能退吗 | payment | 涉及资金/券 |
| 运费谁承担（退货） | aftersales | 场景绑定退货 |
| 运费多少（下单） | logistics | 场景绑定发货 |
| 什么时候发货 | logistics | 包裹动作 |
| 什么时候能退款 | payment | 资金动作 |
| 尺码偏大吗 | product | 商品属性 |
| 换货要多久 | aftersales | 商品处置 |

### 4.5 条件分支拆分

理想做法是按订单状态拆成多条知识对，由 `conditions` 过滤命中：

| pair_id | 条件 | 答案要点 |
|---|---|---|
| `logistics-address-001` | 未发货 | 可直接改，引导进订单详情 |
| `logistics-address-002` | 已发货 | 需联系快递拦截，成功率不确定 |

**v1.3 实际做法（存量迁移）**：同一标准问拆成多条会产生完全相同的检索文本，向量无法区分，只能靠订单状态硬过滤；而订单查询尚未接入（`app/tools/order.py` 仍是固定 mock）。因此先把 5 条状态决策树压成一条“未发货时…；已发货未揽件时…；运输中时…”的分情况话术，让用户对号入座。等订单工具接通、`conditions` 能稳定过滤后，再拆回多条知识对。

### 4.6 话术规范

- 语气：与现有语料一致（“亲～”），单条 40~120 字；
- 每条答案必须包含**一个可执行下一步**（进订单、点售后、联系客服）；
- **禁止裸数字**：时效、金额、比例一律用 `[X]` 占位符，由 `shop_config.yaml` 渲染；
- **禁止承诺词**：保证、一定、百分百、绝对、永久；
- 禁止涉及个人信息收集、发票真伪判断、法律结论。

### 4.7 语料验收标准

| 指标 | 标准 |
|---|---|
| 总量 | 270 条（±5%）；v1.3 阶段值 141 条（产品 80 + 物流 21 + 支付 22 + 售后 18） |
| 子场景覆盖 | 100%，无空白格 |
| 裸数字（时效/金额/比例）/ 承诺词 | 0 条；商品参数数值必须来自事实表 |
| 同义问全局重复 | 0 条（相似度 > 0.92 判定冲突） |
| 答案重复 | 0 组（相似度 > 0.85 判定重复） |
| `sensitive` 人工审核 | 100% |
| 抽样人工通过率 | ≥ 95% |

### 4.8 真值来源（新增，解决“产品咨询无真值”）

产品咨询不再靠模型自由发挥，改为**两层事实表**：

| 事实表 | 内容 | 作用 |
|---|---|---|
| `data/corpus/product_catalog.yaml` | 3 个商品的材质、尺寸、承重、尺码表、护理方式 | 产品参数类答案的唯一来源 |
| `data/mock/orders.jsonl` | 6 个订单，覆盖待支付/待发货/运输中/已签收/退货中/已退款 | 条件分支与订单查询的唯一来源 |

配套规则：

1. 答案中的商品参数必须能在事实表中找到对应字段，否则打回；
2. 价格、库存、活动、发货时效**不得写死**，一律用占位符；
3. 商品事实表中不存在的参数（如具体面料克重、产地），一律回答“帮你确认”或转人工；
4. 订单相关回答只能基于订单事实表字段，禁止编造物流节点与时间。

### 4.9 复合诉求处理规则（新增）

用户一句话跨两个场景时（例：“东西坏了想退，钱什么时候到”）：

1. 分诊只选**主诉求**场景（本例 `aftersales`）；
2. 答案只回答主诉求，次诉求用一句话指路（“退款到账时间可以再问我一次”）；
3. **禁止拼接两个知识对的答案**，避免口径冲突与答案重复；
4. 次诉求若在同一会话中被追问，按普通单场景流程处理。

### 7.1 评测集防虚高方案（新增）

只用中文档里的原话是挡不住虚高的，必须用制度约束：

| 风险 | 做法 |
|---|---|
| 测试问由同一模型生成，分布失真 | 测试问按来源分层：**真实来源 ≥ 60%**（电商“问大家”、评论区提问、客服会话记录改写），合成问 ≤ 40% |
| 生成语料与测试问撞车 | 语料入库前与测试集做相似度比对，`> 0.85` 的测试问直接剔除 |
| 阈值在测试集上调参 | 200 条拆成 **dev 100 / test 100**，阈值与分诊规则只在 dev 上调，test 只跑一次 |
| 只在同商品上测 | 留出泛化集：用未进语料的商品问法（如“这把藤椅多高”）测泛化，单独报告 |
| 只看总体召回 | 分别报告 **真实来源 / 合成来源 / 对抗集** 三组指标；真实与合成差距 > 15 个百分点即判定分布失真 |
| 指标口径太松 | 按“意图命中”而不是“pair_id 完全相等”计分，避免同义知识对误判为未命中 |
| 无法判断提升来源 | 记录随机召回基线（k/N），所有指标必须报告相对基线的提升 |

评测集冻结：生成 `eval_queries.jsonl` 后记录 SHA256，任何语料生成流程都不得读取该文件。

**落地情况（v1.3）**：已实现 `evals/recall_dev.jsonl` / `evals/recall_test.jsonl`（各 32 条，人工口语改写，不复用语料同义问）、dev/test 分离、意图级命中、随机基线（1/N）。尚未实现：真实来源占比统计、0.85 相似度自动剔除、SHA256 冻结校验——这三项在语料继续扩量前补齐。

## 8. 里程碑（分批上线，按阶段不排日期）
