> 关联文档：《PRD-智能客服.md》

## 1. 总体架构

```
客户端（Web 页面 / API 调用方）
        │  POST /chat/stream（SSE）
        ▼
┌───────────────────────────────────────────────────────┐
│ FastAPI 服务层                                         │
│  ├── 会话管理（sessions / messages）                    │
│  └── 编排（/chat 走 LangGraph，/chat/stream 走 pipeline）│
│         │                                               │
│         ├─ 分诊：场景 + 是否追问（LLM）                  │
│         ├─ 召回：query rewrite → 向量检索 top-k          │
│         ├─ 选号：LLM 只输出 pair_id                     │
│         ├─ 取值：代码按 pair_id 取 answer 原文           │
│         └─ 渲染：占位符替换（shop_config.yaml）          │
└───────────────────────────────────────────────────────┘
        │                          │
        ▼                          ▼
  SQLite（业务会话）         SQLite + sqlite-vec（知识库与向量）
```

**保留 v1.0 最值钱的设计**：模型只输出编号，答案由代码取原文。引入向量后仍然如此，这样错误可归因为「召回错 / 选号错 / 改写错」。

## 3. 数据模型

### 3.1 新增四张表（与 `plans` 并存，灰度期双跑）

```sql
-- ① 知识真值表：人可读、可 diff、进 Git
CREATE TABLE kb_pairs (
  pair_id            TEXT PRIMARY KEY,   -- payment-refund-eta-001
  scenario           TEXT NOT NULL,
  sub_scenario       TEXT NOT NULL,
  product_id         TEXT,               -- 产品咨询专用，关联 product_catalog.yaml
  canonical_question TEXT NOT NULL,
  answer             TEXT NOT NULL,
  conditions         TEXT,               -- JSON：{"ship_status": "shipped"}
  keywords           TEXT,               -- JSON 数组
  requires_order     INTEGER DEFAULT 0,
  policy_level       TEXT NOT NULL,      -- stable / configurable / sensitive
  status             TEXT NOT NULL,      -- draft / reviewed / published
  source             TEXT,               -- existing_plan / faq / generated
  version            INTEGER NOT NULL DEFAULT 1,
  updated_at         TEXT NOT NULL
);

-- ② 检索条目：一条知识对拆成 1 条标准问 + N 条同义问
CREATE TABLE kb_docs (
  rowid   INTEGER PRIMARY KEY,
  pair_id TEXT NOT NULL,
  kind    TEXT NOT NULL,                 -- canonical / paraphrase
  text    TEXT NOT NULL,
  text_hash TEXT NOT NULL                -- 增量重建与缓存用
);

-- ③ 向量索引（派生，可整表重建）
CREATE VIRTUAL TABLE kb_vec USING vec0(
  embedding FLOAT[1024],
  scenario TEXT               -- 元数据列（不能写 +scenario，辅助列无法参与 KNN 过滤）
);

-- ④ 索引元数据（防“换模型忘重建”）
CREATE TABLE kb_meta (key TEXT PRIMARY KEY, value TEXT);
-- embed_model / embed_dim / corpus_version / built_at / doc_count
```

**要点**：

- `kb_pairs` 是真值，`kb_vec` 是缓存；删掉索引重建不丢任何数据。
- `rowid` 是 `kb_docs` 与 `kb_vec` 的对齐键，写入时必须显式指定。
- `text_hash` 用于增量重建：文本未变则不重复调 Embedding。

### 3.2 迁移关系（已实现）

| 旧 | 新 | 处理 |
|---|---|---|
| `plans`（62 条，1 条 todo 空方案跳过） | `data/corpus/{logistics,payment,aftersales}_qa.jsonl` → `kb_pairs` | `scripts/migrate_plans.py`：清洗话术（去“告知用户”前缀、去平台名）→ 补同义问 → 产物进 Git，再由 `build_index.py` 同步进 `kb_pairs`，`source=existing_plan`，原编号即 `pair_id` |
| `plans.branches`（5 条含 `${订单发货状态}` / `${订单物流状态}`） | `kb_pairs.answer` 中的“分情况处理”段落 | **不拆成多条知识对**：拆开会让同一标准问出现多份答案，检索无法区分；压成一条分状态话术，由用户对号入座 |
| `plans.todo=1` | 不迁移 | 空正文无法生成答案，留待补写 |
| `shop_config.yaml` | 不变 | 仍负责占位符渲染 |

迁移后的分布：物流 21 条、支付 22 条、售后 18 条，加上产品 80 条，索引共 **141 条知识对 / 623 条检索文档**（标准问 + 同义问）。

### 3.3 订单域模型（真值来源之一）

**订单号规则**：`so` + `YYYYMMDD` + 6 位流水号，共 15 位。例：`so20261101008911` = 2026-11-01 的第 008911 单。

**状态机**：

```
created(待支付) ──支付成功──> paid(待发货) ──发货──> shipped(运输中) ──签收──> delivered(已签收) ──> completed(已完成)
     │                          │                      │
     └─超时未付─> cancelled       └─全额退款─> closed      └─拒收/退回─> after_sales
```

三个正交子状态，避免用一个字段表达所有情况：

| 字段 | 取值 |
|---|---|
| `pay_status` | `unpaid` / `paid` / `refunding` / `refunded` |
| `ship_status` | `unshipped` / `shipped` / `in_transit` / `delivered` / `returned` |
| `aftersales_status` | `none` / `applied` / `approved` / `returning` / `received` / `refunded` / `rejected` |

**关联关系**：

| 关系 | 基数 | 关联键 |
|---|---|---|
| 订单 → 订单明细 | 1 : N | `order_id`，明细含 `product_id` → `product_catalog.yaml` |
| 订单 → 物流 | 1 : 1 | `order_id`，含 `carrier` / `tracking_no` |
| 订单 → 支付流水 | 1 : N | `order_id`，含 `payment_id` |
| 订单 → 售后工单 | 1 : N | `order_id`，工单含 `refund_amount`、退回单号 |

**模拟数据**：`data/mock/orders.jsonl`，6 条覆盖全部关键状态：

| 订单号 | 状态组合 | 用途 |
|---|---|---|
| so20261101008911 | created / unpaid / unshipped | 待支付、取消 |
| so20261101008912 | paid / paid / unshipped | 改地址、发货时效 |
| so20261030008852 | shipped / paid / in_transit | 物流不更新、拦截 |
| so20261028008731 | delivered / paid / delivered | 七天无理由、破损 |
| so20261026008614 | delivered / refunding / returning | 退货中、退款进度 |
| so20261020008402 | completed / refunded / returned | 退款完成 |

规则：售后相关回答只能引用工单字段，不得编造物流节点与到账时间。

### 3.4 商品事实表（真值来源之二）

`data/corpus/product_catalog.yaml` 定义 3 个 SKU 的全部可答参数：

| SKU | 关键事实 |
|---|---|
| `p1_dining_chair` 白蜡木餐椅 | 座高 45cm、座宽 44cm、承重 120kg、E1 级、需组装 15 分钟 |
| `p2_bar_stool` 碳钢升降吧椅 | 座高 63~74cm、底盘 38cm、承重 110kg、PU 面 |
| `p3_dress` 法式碎花连衣裙 | 65% 粘纤 + 35% 亚麻、S~XL 尺码表、30℃ 轻柔洗 |

生成与校验规则：

1. `product_qa.jsonl` 的每条 `answer` 必须能映射到 catalog 字段；
2. 无法映射的问题（如面料克重、产地）不得生成答案；
3. 价格 / 库存 / 活动 / 时效一律占位符，由 `shop_config.yaml` 渲染；
4. `product_id` 写入 `kb_pairs` 与 `kb_vec` 元数据，用于跨商品串味检测。

**跨商品去重**：通用问法（“有现货吗”“多少钱”）在各 SKU 下会重复。处理方式是：标准问与同义问统一带商品前缀（“餐椅有现货吗”），并在检索时优先用会话中的 `last_product_id` 过滤；无上下文时走澄清。

## 4. 语料生产流水线

```
种子抽取 → 缺口盘点 → 分批生成 → 去重 → 规则校验 → 人工审核 → 发布 → 建索引
```

| 步骤 | 脚本 | 输入 → 输出 | 关键规则 | 状态 |
|---|---|---|---|---|
| 种子抽取 | `scripts/migrate_plans.py` | `plans.db` → `data/corpus/*_qa.jsonl` | 保留来源编号，答案只做清洗不改写；同义问带缓存 | 已实现 |
| 缺口盘点 | `scripts/coverage_report.py` | `seeds` + 覆盖矩阵 → 缺口清单 | 每个子场景 ≥ 6 条 | 待实现 |
| 分批生成 | `scripts/gen_corpus.py` | 缺口 → `generated/*.jsonl` | 每批 10~15 条；`temperature=0.3`；只补缺口 | 待实现 |
| 去重 | `scripts/dedupe_corpus.py` | `generated` → 合并结果 | 问法相似 > 0.92 合并；答案相似 > 0.85 人工裁决 | 待实现 |
| 规则校验 | `scripts/validate_corpus.py` | JSONL → 报告 | 裸数字 / 承诺词 / 未登记占位符 / 长度 / 场景冲突 | 待实现 |
| 人工审核 | `review/queue/*.jsonl` | 审核队列 → `status=reviewed` | `sensitive` 100% 必审，其余 10% 抽检 | 待实现 |
| 发布 | `kb_pairs` | `published` | 版本号 +1 | 已实现（迁移条目直接 `published`，产品语料仍 `draft`） |
| 建索引 | `scripts/build_index.py` | `kb_pairs` → `kb_docs` / `kb_vec` | 校验维度，写 `kb_meta`；默认连 `draft` 一起建，上线用 `--published-only` | 已实现 |
| 评测 | `evals/recall_eval.py` | dev/test 集 → 指标 + 阈值建议 | 只用 dev 调阈值，test 只验收 | 已实现 |

### 4.1 生成契约（提示词要点）

```
角色：电商客服知识库语料生成器，只输出 JSONL
约束：
1. 不得写死数字/时效/金额，一律用 [X] 占位符
2. 不得新增承诺（保证/一定/百分百/绝对）
3. 涉个人信息、发票真伪、法律结论 → 输出 {"skip": true}
4. answer 40~120 字，必须含一个可执行下一步
5. paraphrases 3~5 条，覆盖口语、错别字、简称、省略
6. 与种子答案冲突时，以种子为准，仅做口语化改写
```

### 4.2 质量闸门

| 闸门 | 判定 | 动作 |
|---|---|---|
| 裸数字 | 时效/金额/比例出现非占位符数字（商品参数除外） | 打回 |
| 承诺词 | 含保证/一定/百分百/绝对/永久 | 打回 |
| 占位符 | 无法在 `shop_config.yaml` 找到映射 | 打回 |
| 长度 | < 30 或 > 150 字 | 打回（例外：存量迁移的“分情况处理”话术 ≤ 320 字，含 3~4 个状态分支） |
| 下一步动作 | 缺少“进订单/点售后/联系客服” | 打回 |
| 同义问冲突 | 跨 pair 相似度 > 0.92 | 合并到更具体的一条 |
| 答案重复 | 相似度 > 0.85 | 合并或人工裁决 |
| 场景冲突 | 问法与 scenario 关键词不符 | 打回并重新分诊 |

## 5. Embedding 接入

### 5.1 供应商与参数

| 项 | 值 |
|---|---|
| 供应商 | 阿里云百炼 |
| 模型 | `text-embedding-v4` |
| 维度 | 1024（可选 2048/1536/1024/768/512/256/128/64） |
| Base URL | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| 单批上限 | **10 行**（v4 硬限制） |
| 单行上限 | 8192 tokens |
| 归一化 | 入库前单位化，L2 距离等价余弦 |
| 计费 | 0.0005 元/千 token；新用户 100 万 token / 90 天 |

已在真实 Key 上验证：HTTP 200、维度 1024、10 条批量成功、10 条短句 52 tokens。

### 5.2 统一入口 `app/llm/embedding.py`

```python
"""Embedding 统一入口：OpenAI 兼容协议。"""
import math
from openai import OpenAI
from app import config

_client = OpenAI(
    base_url=config.EMBED_BASE_URL,
    api_key=config.EMBED_API_KEY,
    timeout=30,
    max_retries=2,
)

def _prepare(text: str) -> str:
    return " ".join(text.split())[:1000]

def _normalize(vec: list[float]) -> list[float]:
    norm = math.sqrt(sum(v * v for v in vec)) or 1.0
    return [v / norm for v in vec]

def embed_documents(texts: list[str]) -> list[list[float]]:
    vectors = []
    for i in range(0, len(texts), config.EMBED_BATCH):
        batch = [_prepare(t) for t in texts[i : i + config.EMBED_BATCH]]
        resp = _client.embeddings.create(
            model=config.EMBED_MODEL,
            input=batch,
            dimensions=config.EMBED_DIM,
            encoding_format="float",
        )
        vectors.extend(_normalize(d.embedding) for d in resp.data)
    return vectors

def embed_query(text: str) -> list[float]:
    return embed_documents([text])[0]
```

约束：`EMBED_BATCH` 必须 ≤ 10；查询与入库**必须同一模型同一维度**。

### 5.3 配置项

```bash
EMBED_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
EMBED_API_KEY=sk-****           # 只存 .env
EMBED_MODEL=text-embedding-v4
EMBED_DIM=1024
EMBED_BATCH=10
RETRIEVAL_MODE=vector           # plans | vector，灰度开关
RECALL_THRESHOLD=0.70           # 全局兜底
# 场景级阈值：不同语料分布不能复用同一个值（evals/recall_eval.py --calibrate 产出）
RECALL_THRESHOLD_PRODUCT=0.60
RECALL_THRESHOLD_LOGISTICS=0.56
RECALL_THRESHOLD_PAYMENT=0.71
RECALL_THRESHOLD_AFTERSALES=0.71
```

**占位符支持整句片段**：`shop_config.yaml` 的 key/value 不限于数字，可以映射整句话术片段。例如 `"[发货时效]": "48小时内发货"`、`"[库存状态]": "现货，可当日发出"`。这样避免 `[X]个工作日` 渲染成“48小时个工作日内”这类病句。

## 6. 索引构建 `scripts/build_index.py`

| 步骤 | 动作 |
|---|---|
| 1 | 读取 `kb_pairs` 中 `status IN (published, reviewed[, draft])`；默认含 `draft`（联调期产品语料仍是草稿），上线加 `--published-only` |
| 2 | 组装 embed 文本：`scenario + sub_scenario + canonical_question + paraphrases + keywords`（**answer 不进向量**） |
| 3 | 全量：清空 `kb_docs` / `kb_vec`；增量：按 `text_hash` 只处理变更 |
| 4 | `embed_documents` 批量取向量（每批 10） |
| 5 | 写 `kb_docs`，再写 `kb_vec`（显式 rowid 对齐） |
| 6 | 写 `kb_meta`：模型、维度、语料版本、构建时间、条数 |
| 7 | 输出统计：条数、维度、耗时、失败数 |

**启动自检**：`kb_meta.embed_dim != config.EMBED_DIM` 时拒绝服务并提示重建，防止换模型后召回全乱。

**成本量级**：当前 141 条知识对 → 623 条检索文档，约 2.8 万 token，一次全量构建约 0.02 元、20 秒左右；扩到 270 条约 1.2 万文档，成本仍可忽略。

## 7. 在线召回链路

### 7.1 流程

```
用户消息
 → 分诊（场景 + is_followup + confidence）
 → 若为追问：query rewrite（拼 active_scenario + 上轮主题）
 → embed_query
 → kb_vec KNN（k=20，scenario 过滤）
 → 按 pair_id 去重，取最小距离
 → 阈值按场景取（产品 0.60 / 物流 0.56 / 支付 0.71 / 售后 0.71），保留 top-5
 → 分差判定：top1 - top2 ≥ 0.05 时直接取 top1，跳过选号调用
 → 分差不足时 LLM 选号（只输出 pair_id 或 null）
 → 若有 last_product_id，先按 product_id 过滤，避免跨商品串味
 → 代码取 answer 原文
 → 条件分支过滤（conditions 与订单状态匹配）
 → shop_config.render
 → 返回 / SSE
```

### 7.2 检索 SQL

```sql
SELECT d.pair_id, d.kind, d.text, v.distance
FROM kb_vec v
JOIN kb_docs d ON d.rowid = v.rowid
WHERE v.embedding MATCH ?
  AND k = 20
  AND v.scenario = ?
ORDER BY v.distance;
```

**距离换算**：`kb_vec` 存归一化向量，`distance` 是 L2 距离，相似度 `score = 1 - d²/2`（等价余弦）。阈值比较一律用 `score`，不要直接拿 `distance` 跟 0.70 比。

**实测校准**：`text-embedding-v4` 对短中文问句的余弦普遍偏低（同义改写 0.55~0.75，原句复述 0.85~0.99），初始统一阈值 0.70 会让大量正确召回落在门外。现改为场景级阈值，由 dev 集扫出（见 §7.3）。

### 7.3 阈值校准与评测（已实现）

**评测集**：`evals/recall_dev.jsonl` / `evals/recall_test.jsonl`，各 32 条（四场景各 8 条），字段 `{q, scenario, expect}`。问法为人工口语改写，不复用 `kb_pairs.paraphrases`，避免“拿训练集考自己”。

**评测脚本**：`evals/recall_eval.py`，只跑“embed → KNN → top-k”，不调分诊与选号模型，因此结果确定、可回归。

| 指标 | 口径 |
|---|---|
| R@1 / R@3 / R@5 | 期望 `pair_id` 是否出现在前 k 个候选 |
| 意图@1 | top1 与期望同场景、同子场景（商品还要同 `product_id`）——问“承重多少”命中“体重大能坐吗”算对 |
| MRR | 期望 `expect` 排名倒数均值 |
| 跨意图误答 | top1 分数 ≥ 阈值，但意图不一致；最危险的指标 |
| 随机基线 | 1 / 该场景知识对数（商品 0.013、物流 0.048、支付 0.045、售后 0.056） |

**实测结果**（2026-11-01，141 条知识对）：

| 集合 | R@1 | 意图@1 | R@3 | R@5 | MRR |
|---|---|---|---|---|---|
| dev（32） | 81.2% | 93.8% | 96.9% | 96.9% | 0.891 |
| test（32） | 96.9% | 96.9% | 100% | 100% | 0.984 |

**校准规则**：阈值只允许在 dev 上扫（0.30~0.90，步长 0.01）；要求作答率 ≥ 80%，最大化 `意图答对 − 意图答错`，平手取更高阈值。test 集只在验收时跑一次。

扫出的值：产品 0.60、物流 0.56、支付 0.71、售后 0.71。产品/物流偏低是因为语料口语化、短问句余弦普遍在 0.6~0.8；支付/售后话术模板化，正负样本分得开。**这组值不可跨场景复用，也不可跨语料版本复用**——每次语料有实质变更都要重扫。

**残差**：test 集 3 条正确答案落在阈值下（“要上传什么凭证” 0.615、“退款一直没到” 0.589、“网络超时支付不了” 0.666），会走 L2 澄清而不是硬答，属于“宁可多问一句”的取舍；1 条同商品近意图误答（0.742）。

**条件化选号（省一次模型调用）**：

| 条件 | 动作 | 理由 |
|---|---|---|
| top1 - top2 ≥ 0.05 | 直接取 top1 | 分差足够大时模型几乎不会翻盘，省 300ms 左右 |
| 0 < top1 - top2 < 0.05 | 调 LLM 在 top-5 内选 | 边界情况需要语义判断 |
| top1 < 场景阈值 | 不选号，走兜底 | 避免低分硬答 |

### 7.4 兜底策略

| 情况 | 行为 |
|---|---|
| top1 ≥ 0.80（`MID_CONFIDENCE`） | 直接答，不加限定语 |
| 场景阈值 ≤ top1 < 0.80 | 答完加一句“如果不一致，把订单号发我，我帮你核实” |
| top1 < 场景阈值 但有次优候选 | 展示 2~3 个相似问题让用户选（L2） |
| 无候选 | 澄清一次 → 仍无 → 转人工（L3 → L4） |
| 模型返回 null / 条件不匹配 | 转人工，不硬答（L4） |

## 12. 运维

| 项 | 做法 |
|---|---|
| 新增知识 | 直接写 `kb_pairs`（`status=draft`）→ 审核 → `published` → `/admin/reindex` |
| 语料上线 | 按 B1（餐椅）→ B2（吧椅）→ B3（连衣裙）→ B4（其余三场景）分批，每批过闸门再进下一批 |
| 商品参数变更 | 改 `product_catalog.yaml` → 重跑 `validate_corpus.py` → 重建受影响的知识对 |
| 改时效/金额 | 改 `shop_config.yaml`，无需重建索引 |
| 换 Embedding 模型 | 改 `.env` → 全量重建（维度不同需重定表结构）→ 重跑评测 |
| 备份 | 备份 `plans.db` + `kb_pairs` 导出 JSONL；索引可不备份 |
| 排障 | 日志记录 `query / rewritten_query / top5(pair_id,score) / chosen / fallback_reason` |

## 13. 风险

| 风险 | 对策 |
|---|---|
| 产品咨询无真值，模型编参数 | 只生成通用属性；具体型号参数转人工；抽检 20% |
| 换模型忘重建导致召回乱 | `kb_meta` 维度校验，不一致拒绝启动 |
| 语料重复导致答案摇摆 | 去重阈值 0.92 / 0.85 + 人工裁决 |
| 阈值不合适 | 场景级阈值由 dev 集扫描得出，语料变更后重扫；test 集只验收 |
| 单批超 10 条报错 | `EMBED_BATCH=10` + 代码分批 + 重试 |
| Key 泄露 | 仅 `.env`；已暴露 Key 轮换 |
| 向量索引与真值不一致 | 索引只由脚本生成，禁止手改 |
